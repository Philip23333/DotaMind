> 状态说明（2026-08-11）：本文冻结在 v2.5 收尾时的 19 工具能力快照，用于保留
> V3.0 缺口与优先级判断，不是当前注册表。当前 registry 为 25 个工具，已增加 Valve
> Catalog 英雄/技能/天赋/物品工具与请求级 History Lookup；当前能力以代码和最新
> progress 为准。

> 目标:V3.0 = "基础的完整功能闭环"。本文盘点当前工具/契约覆盖了哪些查询、哪些常见查询**接不上**(planner 只能回 `insufficient_tools`),并给出 V3.0 工具路线图与首个切片建议。
>
> "闭环"定义:用户查询 → planner 能选出工具 → 工具产出 evidence → critic 通过 → answer。任何一环缺工具 = 缺口。

## 2. 缺口分析(按"接不上"严重度排序)

### 🔴 P0 — 高频核心缺口(直接对应 V3.0 用户蓝图)

**G1. 英雄出装攻略(item / talent / skill build)**
- 查询样例:"Lina 出什么装?"、"PA 几号位核心装 + 天赋怎么点"、"冰魂辅助装流派"。
- 现状:**无任何工具**。`patch.item_changes` 只讲版本改动,不是 build。
- 需要的 evidence:`item_build`(核心/ situational / 起手 / 中立)、`talent_build`、`skill_build`。
- 数据源可行性:**STRATZ 可行,需 schema 探查**。`stratz_schema_reference.md` 目前只覆盖 heroStats/laneOutcome/matchup/stats(我们已用的);build 数据(物品流行度/ timings)在 2.1MB introspection 里但未定位具体 query。需要先跑 `apps/api/scripts/stratz_schema_docs.py` 找到 item-build 入口(`heroStats.itemBuild` / `itemPopularity` / item timings 之类)。
- 复杂度:中(需新 STRATZ query + 集成层 + agentic 工具 + evidence-first 透传)。

**G2. 玩家战绩查询(player profile + recent matches + hero performance) ✅ 已实现(2026-07-08)**
- 查询样例:"853634884 概览"、"查 853634884 最近 20 场"、"853634884 近 20 场什么英雄胜率高"、"最近一周什么英雄胜率高"。
- 数据源:**STRATZ**(统一 provenance 口径;**非 OpenDota** —— OpenDota `/players/{id}/heroes` 是 lifetime 不适合"最近")。schema inventory:`docs/technical/stratz_player_page_graphql_inventory.md`。
- 已交付 3 工具(steamAccountId 数字直查):
  - `stratz.player_profile` → `player_identity`(global_win_rate 本地派生 winCount/matchCount)。
  - `stratz.player_recent_matches` → `player_recent_match`(win = native `MatchPlayerType.isVictory`,不推导)+ `player_recent_summary`(wins/losses/match_count)+ `sample_size`。
  - `stratz.player_hero_performance` → `player_hero_performance`(win_rate 本地派生 winCount/matchCount)+ `sample_size`;双 take(outer=hero rows / `match_take`=stat 样本)。
- 段位过滤(两个值空间,不混):recent_matches 走 `bracketIds`(0-8,`basic_to_bracket_ids`);hero_performance 走 `rankIds`(0-80,`basic_to_rank_ids`,**LIVE-LOCKED**:`bracket*10+star`,Immortal={80},`*5-*9` 空隙)。
- v1 边界(留后续):不做名搜索(非数字 query → `insufficient_tools`);不支持 region/game_mode(QueryContext 是字符串枚举 vs request 要 `[Int]`/`[Byte]`,`validate_context_scope` 已拒);不设 `weeks_back`;`min_match_count` 不纳入 sample_policy(另配)。
- 复杂度:中(STRATZ query + 集成层 + 3 工具 + evidence-first 透传 + rankIds live-lock)。

### 🟡 P1 — 中频,补上后"闭环感"显著提升

**G3. ban/pick 率 meta(选取/禁用热度)**
- 查询样例:"这版本什么英雄非 ban 必选?"、"Lina 出场率多高"。
- 现状:**部分**。STRATZ heroStats 暴露 pickCount/banCount,但 `stratz.hero_position_stats` 只透传 matchCount/winCount,没带 ban/pick。前一个用例的回答里就主动声明了"未涉及禁用率/选取率"。
- 方案:扩 `hero_position_stats` 的 value 加 ban/pick 字段(evidence-first 加列,非新工具),或新 `stratz.hero_pick_ban_meta`。
- 复杂度:低(主要是集成层补字段 + evidence 透传)。

**G4. 单局详情(match detail)**
- 查询样例:"这场 XXX 的出装/经济曲线"、"match_id=... 的细节"。
- 现状:**集成层已存在**(`OpenDotaTeams.get_match_detail(match_id)` 已实现,`team_report.match_details` policy 也有),但**没暴露成 agentic 工具**。
- 方案:包一层 `opendota.match_detail` 工具 + `match_detail` evidence。低 effort。
- 复杂度:低(集成层现成,只差工具壳 + evidence)。

### 🟢 P2 — 低频或高复杂,排到 V3.x

- **G5. 阵容评分(5v5 draft evaluation)**:需要 pairwise synergy+counter 矩阵组合成 5v5 分。和"thin relay、不打综合分"原则冲突(会发明聚合分)。复杂,留 V3.x+,需单独设计。
- **G6. 物品 meta(item-centric win rates)**:"这版本什么装备强"。可从 match 数据派生。低优先。
- **G7. 职业赛事(tournament/series)**:有 team 工具但无赛事/联赛工具。可能超出"基础闭环"范围。

## 4. 跨切面基础(建议与新工具并行/前置)

- **A. §7.2 critic→planner retry 回环(`max_replans=1`)**:新工具(G2 玩家战绩尤其)容易产出稀疏 evidence(玩家近期场次少);retry 回环让 critic 判稀疏后能让 planner 补工具/放宽阈值再跑。这是 V3.1 critic 优化的前置,但对新工具的健壮性起底——建议**与 P0 并行或紧跟其后**。见 v2.5 设计 §7.2 + Sample Policy 阶段 2。
- **B. Prompt 收敛(暂停中)**:加 2~4 个新工具 = planner prompt 更长;先收敛到 `app/agentic/prompts/` 能让增量更可控。非阻塞,但建议在新工具上线前做。
- **C. `resolve_player` 解析器**:和 `resolve_hero`/`resolve_team` 同构。G2 v1 走 steamAccountId 数字直查,**未做名搜索**;`resolve_player` 作为 player v2 的独立切片(让"查 Arteezy 战绩"类名查询走通)。

## 5. V3.0 首个切片(已执行)

**已选:P0-b 玩家战绩(G2)** 作为第一刀 —— ✅ 已交付(2026-07-08)。最终落地与初版设想的偏差:
1. 数据源由 **OpenDota 改为 STRATZ**(统一 provenance 口径;OpenDota `/players/{id}/heroes` 是 lifetime,不适合"最近")。详见上方 G2 段。
2. **未做 `resolve_player` 名搜索**:v1 走 steamAccountId 数字直查(非数字 query → `insufficient_tools`),名搜索留 v2。降低了首切复杂度,代价是用户必须提供数字 ID。
3. rankIds(0-80)段位过滤是 **HARD GATE**,经 live query 锁定(`bracket*10+star`,Immortal={80})后已实现;若当时锁不定则 hero_performance 的 bracket 过滤会按计划回退为不实现。
