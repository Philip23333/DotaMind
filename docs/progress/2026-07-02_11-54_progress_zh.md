## 触发：一次 query 测试

针对 `POST /api/v1/plan` 测试 query：

```text
骷髅王和冰魂走一条路怎么样？在传奇分段的胜率怎么样
```

planner 给出 plan（`intent=lane_synergy`、`output_contract=natural_language_answer`）：

```text
resolve_sk = resolve_hero("骷髅王")          # → hero_id 42
resolve_aa = resolve_hero("冰魂")            # → hero_id 68
lane_partner = stratz.lane_outcome(
    hero_id="$resolve_sk.data.hero.hero_id",
    is_with=true,
    bracket_basic_ids=["LEGEND_ANCIENT"],
)
```

`stratz.lane_outcome` 返回 125 行（SK 作为 heroId1 的全部搭档），冰魂
（heroId2=68）是其中一行。最终 answer 给出 ≈57.8%/≈728 场，**结论方向正确**。

## 纠正：hero ID 映射

本轮早些时候的分析曾把 `hero_id=68` 当成虚空假面（Faceless Void），并据此
误判 answer "挑错了记录、把虚空的数据当成冰魂"。

权威来源 [apps/api/app/data/heroes/dota2_heroes.yaml](apps/api/app/data/heroes/dota2_heroes.yaml)：

- `id: 42` → Wraith King / 骷髅王
- `id: 68` → Ancient Apparition / 冰魂 / 远古冰魄
- `id: 76` → Outworld Devourer / 黑鸟

`68 = AA` 是对的，`76 = OD`。前一轮"answer 编造数据"的判断**不成立**，系统
对该 query 的实际回答是正确的。已向用户致歉并修正。

## 系统真实状态

虽然这次答对了，分析过程中暴露的结构性问题仍然成立：

1. **`$resolve_aa` 在 plan 层是死调用**。`lane_partner` 只引用了
   `$resolve_sk.data.hero.hero_id`，AA 的解析结果没有被任何下游 tool_call 的
   args 引用。
2. **`resolve_hero` 的副作用救了 query**。`resolve_hero_evidence` 为 AA 产出
   一条 `hero_identity` evidence（含 `hero_id=68, localized_name=Ancient
   Apparition, aliases=[..., "冰魂", ...]`），LLM 据此在 252 条 evidence 里
   隐式做 name→id→row 的 join。
3. **synthesizer 全量喂 LLM、无程序化抽取、无反向核对**。
   [answer/synthesizer.py:394-415](apps/api/app/agentic/answer/synthesizer.py)
   把整个 `evidence_graph` 序列化喂给 LLM，`natural_language_answer` 的
   `claims/recommendations/limitations` 全空，critic 无法把 summary 里的数字
   反查到具体 evidence_id。
4. **critic 阈值放行**。`confidence=0.41 < 0.50` 但 `passed=True severity=
   warning`，response `status=ok`。
5. **STRATZ 数据小时级漂移**。同一 query 在数小时内 AA 行从 727/0.5791 →
   728/0.5783 → 797/0.5797。测试断言不能用精确数字。

## STRATZ laneOutcome 是否支持双英雄过滤：实证

通过 [StratzTransport](apps/api/app/integrations/stratz/transport.py) 对
`https://api.stratz.com/graphql` 发起 schema introspection，结论：

`HeroStatsQuery.laneOutcome` 字段**只有 5 个 args**：

```text
- heroId: Short
- isWith: Boolean!
- week: Long
- bracketBasicIds: [RankBracketBasicEnum]
- positionIds: [MatchPlayerPositionType]
```

尝试 `heroId2`、`heroIds` 两种双英雄入参形态，均被服务端直接拒绝：

```text
Unknown argument 'heroId2' on field 'laneOutcome'. Did you mean 'heroId'
Unknown argument 'heroIds' on field 'laneOutcome'. Did you mean 'heroId'
```

**结论：laneOutcome 在 GraphQL 层不支持双英雄过滤**。响应里的 `heroId1` /
`heroId2` 是行数据字段，不是入参。`pair_lane_outcome` 工具若要落地，必须
"fetch by hero1 → handler 内 client-side filter 到 partner_hero_id"，无法
在 GraphQL 层一次只取 1 行。

`heroVsHeroMatchup` 是否同样受限本轮未验证，作为 follow-up。

## 设计提案

### 1. ExecutionPlan 引入 QueryContext

scope filter（bracket/week/position/region/game_mode）上提到 plan 层，工具
input_model 不再含这些字段。handler 签名 `(args, context)`，executor 在 schema
校验前注入 `plan.context`。

```python
class QueryContext(BaseModel):
    bracket: list[str] | None = None
    week: int | None = None
    position_ids: list[str] | None = None
    region_ids: list[str] | None = None
    game_mode_ids: list[str] | None = None
```

### 2. STRATZ 工具按能力重切（替换现有两个工具）

| 工具 | 问题参数（input_model） | evidence_kinds | 内部实现 |
|---|---|---|---|
| `stratz.pair_lane_outcome` | `hero_id`, `partner_hero_id`, `is_with` | `pair_lane_winrate`, `sample_size` | laneOutcome(heroId=hero1) → client-side filter 到 partner |
| `stratz.hero_matchup_ranking` | `hero_id`, `side: with\|vs`, `take`, `min_sample_size` | `matchup_ranking_row`, `sample_size` | heroVsHeroMatchup(heroId, take) |
| `stratz.lane_meta_global` | `is_with`, `min_sample_size`, `highlight_top` | `lane_meta_row`, `sample_size` | laneOutcome（无 heroId）→ handler 内聚合 + top-N |
| `stratz.hero_position_stats` | （无） | `position_stat` | stats(groupByPosition) |

退役：`stratz.lane_outcome`、`stratz.hero_vs_hero_matchup`（按 AGENTS.md 不留
兼容层）、`lane_outcome` / `matchup_win_rate` evidence kind、相关 contract。

### 3. 工具输出形态按问题塑形，而非返回原始 records

- pair_lane_outcome：1 行 lookup，无 `take`。
- hero_matchup_ranking：take 控制的 top-N，已排序。
- lane_meta_global：**聚合统计 + top-N 高亮**，不返回原始 120 行。
- ToolResult 增加 `data_truncation` 与 `total_available`，让 critic 和 planner
  知道有没有"未看到的尾部"。

### 4. 锁定的默认值（本轮决定）

- `hero_matchup_ranking.take`：default 10、max 50、`min_sample_size` default 100
- `lane_meta_global.highlight_top`：default 15、`min_sample_size` default 200
- `pair_lane_outcome`：无 take；不强制 min_sample_size，但 critic 在 < 50 时
  降 confidence

### 5. Critic 新增 plan-level 规则

- context-goal 一致性：goal 提到分段/时间，`plan.context` 必须对应。
- pair 实体覆盖：goal 提到两个英雄，plan 必须含两个 `resolve_hero` + 一个
  `pair_*` 工具同时引用两者。
- confidence < 阈值 → `severity=failed` 且 `passed=false`（当前是 warning
  + passed=true，是 bug）。

### 6. Replan 路径

`total_available + data_truncation` 暴露截断状态，critic 在"目标实体未在
returned records 内 且 truncated=true"时给 `replan_hint: "bump take on tool X"`。
planner 只改一个 tool_call 的 `take`，QueryContext 不动，其它 tool_call 不动。
匹配 v2.5 §7.2 `max_replans=1, max_tool_calls_total=8` 上限。

### 7. synthesizer 强制 claims

`natural_language_answer` 必须把 summary 里每个数字挂在 `claims[].evidence_refs`
上，critic 才能反查。否则继续允许 LLM 自由文本 → 不可校验。
