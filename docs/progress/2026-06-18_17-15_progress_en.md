## Work Completed This Session

### 1. Team Query Pipeline Clarification

The current natural-language team query pipeline is:

```text
POST /api/v1/query
  -> QueryService
  -> Orchestrator LLM function calling
  -> ReportRequest(task_type="team_report", team_name=raw extracted value)
  -> ReportPipeline
  -> Retriever
  -> OpenDota team directory + deterministic resolution
  -> OpenDota team facts
  -> Analyzer
  -> Critic
  -> Formatter
  -> HTTP response
```

The Orchestrator only selects `get_team_report` and extracts the user's expression, such as `"Team BB"`. It does not generate or guess an OpenDota `team_id`.

The Retriever maps that expression to a real OpenDota team and retrieves factual data after resolution succeeds.

### 2. Deterministic Team Candidate Matching

The Retriever now uses staged deterministic matching:

1. Raw name/tag exact match
2. Case, whitespace, and punctuation normalization
3. Removal of generic words such as `Team`, `Esports`, and `Gaming`
4. Compact-string matching
5. CamelCase acronym recall, for example `BetBoom -> BB`
6. Fuzzy matching with `SequenceMatcher`
7. Resolution based on match strength

Resolution has three states:

```text
resolved   -> one team_id, continue retrieval
ambiguous  -> multiple plausible candidates
not_found  -> no plausible candidate
```

`Team BB` currently recalls:

```text
team_id=8255888  name=BB       tag=BB
team_id=9131584  name=BB Team  tag=BB
```

When candidates have equal match strength, the system returns ambiguity instead of guessing from rating.

### 3. Team Error Contract

Team retrieval no longer hides failures behind a fixed Team Spirit mock:

| Scenario | HTTP status | Error code |
|---|---:|---|
| Unique match | 200 | - |
| Multiple plausible candidates | 409 | `ambiguous_team` |
| No match | 404 | `team_not_found` |
| Live data disabled or OpenDota unavailable | 503 | `team_data_unavailable` |

Error responses contain:

```json
{
  "error": "ambiguous_team",
  "message": "Multiple OpenDota teams matched 'Team BB'.",
  "requested_team": "Team BB",
  "candidates": []
}
```

The meta report mock fallback remains unchanged. This session only removed the silent team report mock fallback.

### 4. Aggressive OpenDota Split

The original monolithic file was deleted:

```text
app/integrations/opendota.py
```

The transitional compatibility layer was also deleted:

```text
OpenDotaClient
opendota/client.py
all proxy methods and private compatibility methods
```

The current structure is:

```text
app/integrations/opendota/
  __init__.py
  transport.py
  heroes.py
  teams.py
```

Responsibilities:

| Module | Responsibility |
|---|---|
| `transport.py` | AsyncClient, API key, timeout, cache, request logs, connection shutdown |
| `heroes.py` | heroStats, role inference, win/pro metrics, hero_id-to-name mapping |
| `teams.py` | teams, matches, players, match details, team metric aggregation |

The Retriever explicitly assembles the components:

```python
transport = OpenDotaTransport(base_url, api_key)
heroes = OpenDotaHeroes(transport)
teams = OpenDotaTeams(transport, heroes)
```

Calls now target domain services directly:

```python
self._opendota_heroes.get_stats_for_role(role)
self._opendota_teams.get_all()
self._opendota_teams.get_report_data(...)
```

No `OpenDotaClient` or legacy method references remain in the project.

### 5. Shared HTTP Connections and Application Lifecycle

Previously, each OpenDota endpoint created a new `httpx.AsyncClient`, preventing TCP/TLS connection reuse.

`OpenDotaTransport` now lazily creates one shared client. Hero and team services share its connection pool and cache.

Shutdown path:

```text
FastAPI lifespan
  -> QueryService / ReportService
  -> ReportPipeline
  -> Retriever
  -> OpenDotaTransport.aclose()
  -> httpx.AsyncClient.aclose()
```

Current configuration:

```text
CACHE_TTL = 3600 seconds
REQUEST_TIMEOUT_SECONDS = 20
```

The timeout applies to each individual HTTP request, not the total team report duration.

## Current End-to-End Team Pipeline

```text
User query
  -> Orchestrator extracts team_name
  -> Retriever calls OpenDotaTeams.get_all()
  -> OpenDotaTransport GET /teams
  -> Retriever deterministic resolution
      -> resolved / ambiguous / not_found
  -> OpenDotaTeams.get_report_data()
      -> GET /teams/{team_id}/matches
      -> filter by time window, cap at 30 matches
      -> GET /teams/{team_id}/players
      -> concurrent GET /matches/{match_id}
      -> OpenDotaHeroes.name_map()
      -> GET /heroStats
      -> aggregate record, heroes, players, duration, and adaptation metrics
  -> Analyzer creates TeamReport
  -> Critic approves team report
  -> Formatter attaches OpenDota/live source
  -> HTTP response
```

## Known Issues

1. **OpenDota upstream variance**: `/teams/{id}/players` has produced both 5-second `ConnectError` and 20-second `ReadTimeout`, while later calls to the same endpoint can complete in under one second.
2. **High cold-request latency**: A successful full Team Liquid report took about 40 seconds, with the players endpoint close to the 20-second limit.
3. **Concurrent match details**: Up to 30 match details are fetched concurrently. Individual failures are ignored, which may reduce the completeness of hero statistics.
4. **No ambiguity interaction loop**: The API returns candidates, but the request contract cannot yet resubmit a selected `team_id`.
5. **Weak team critic**: The Critic does not currently perform evidence-level review for team reports.

## Recommended Next Steps

1. Collect success rate, P50, P95, and error types per OpenDota path to establish an upstream stability baseline.
2. Add a `team_id` selection and resubmission contract for ambiguous results.
3. Design partial-data degradation so a players or match-detail failure is reported explicitly without always aborting the entire report.
4. Decide on bounded retries, backoff, and concurrency limits only after enough diagnostic samples are available.
5. Add evidence and Critic validation to team reports.
