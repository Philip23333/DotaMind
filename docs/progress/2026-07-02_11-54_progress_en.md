## Trigger: one query test

Tested `POST /api/v1/plan` with:

```text
骷髅王和冰魂走一条路怎么样？在传奇分段的胜率怎么样
```

The planner produced (`intent=lane_synergy`, `output_contract=natural_language_answer`):

```text
resolve_sk = resolve_hero("骷髅王")          # → hero_id 42
resolve_aa = resolve_hero("冰魂")            # → hero_id 68
lane_partner = stratz.lane_outcome(
    hero_id="$resolve_sk.data.hero.hero_id",
    is_with=true,
    bracket_basic_ids=["LEGEND_ANCIENT"],
)
```

`stratz.lane_outcome` returned 125 rows (all partners of SK as heroId1);
Ancient Apparition (heroId2=68) was one of them. The final answer reported
≈57.8% / ≈728 matches. **The answer was directionally correct.**

## Correction: hero id mapping

Earlier analysis in this session wrongly identified `hero_id=68` as Faceless
Void, and on that basis incorrectly concluded the answer "picked the wrong
record / reported Faceless Void data as Ancient Apparition."

Authoritative source
[apps/api/app/data/heroes/dota2_heroes.yaml](apps/api/app/data/heroes/dota2_heroes.yaml):

- `id: 42` → Wraith King / 骷髅王
- `id: 68` → Ancient Apparition / 冰魂 / 远古冰魄
- `id: 76` → Outworld Devourer / 黑鸟

`68 = AA` is correct; `76 = OD`. The earlier "answer fabricated data" claim
**does not hold**; the system answered this query correctly. Acknowledged
the error and corrected.

## System's actual state

The answer was correct, but the structural issues surfaced during analysis
remain real:

1. **`$resolve_aa` is dead as an arg reference**. `lane_partner` references
   only `$resolve_sk.data.hero.hero_id`; no downstream tool_call consumes
   AA's resolved id via arg reference.
2. **`resolve_hero`'s evidence side-effect saved the query**.
   `resolve_hero_evidence` emits a `hero_identity` evidence for AA
   (`hero_id=68, localized_name=Ancient Apparition, aliases=[..., "冰魂",
   ...]`). The LLM uses that to do an implicit name→id→row join over the
   252-item evidence dump.
3. **synthesizer feeds the full graph to the LLM with no programmatic
   extraction or back-checking**.
   [answer/synthesizer.py:394-415](apps/api/app/agentic/answer/synthesizer.py)
   serializes the entire `evidence_graph` into the LLM prompt, and the
   `natural_language_answer` contract leaves `claims/recommendations/
   limitations` empty — the critic cannot back-check the summary's numbers
   against any evidence_id.
4. **Critic threshold leaks**. `confidence=0.41 < 0.50` but `passed=True
   severity=warning`; the response is `status=ok`.
5. **STRATZ data drifts on an hour-scale**. The same query saw the AA row
   shift from 727/0.5791 → 728/0.5783 → 797/0.5797 within hours. Tests
   cannot assert exact numbers.

## Whether STRATZ laneOutcome supports pair filtering: empirical result

Ran schema introspection against `https://api.stratz.com/graphql` via
[StratzTransport](apps/api/app/integrations/stratz/transport.py).

`HeroStatsQuery.laneOutcome` has exactly **5 args**:

```text
- heroId: Short
- isWith: Boolean!
- week: Long
- bracketBasicIds: [RankBracketBasicEnum]
- positionIds: [MatchPlayerPositionType]
```

Both candidate pair-filter shapes were rejected by the server:

```text
Unknown argument 'heroId2' on field 'laneOutcome'. Did you mean 'heroId'
Unknown argument 'heroIds' on field 'laneOutcome'. Did you mean 'heroId'
```

**Conclusion: laneOutcome does not support pair filtering at the GraphQL
layer.** `heroId1` / `heroId2` in the response are row data fields, not
inputs. A `pair_lane_outcome` tool must "fetch by hero1 → client-side
filter to partner_hero_id" inside the handler; it cannot reduce to 1 row
at the GraphQL layer.

Whether `heroVsHeroMatchup` is similarly restricted was not verified this
round; left as follow-up.

## Design proposal

### 1. Add QueryContext to ExecutionPlan

Lift scope filters (bracket/week/position/region/game_mode) to plan level.
Tool `input_model` no longer carries these. Handler signature becomes
`(args, context)`; the executor injects `plan.context` before schema
validation.

```python
class QueryContext(BaseModel):
    bracket: list[str] | None = None
    week: int | None = None
    position_ids: list[str] | None = None
    region_ids: list[str] | None = None
    game_mode_ids: list[str] | None = None
```

### 2. Reshape STRATZ tools around capabilities (replacing the two current tools)

| Tool | Question params (input_model) | evidence_kinds | Internal impl |
|---|---|---|---|
| `stratz.pair_lane_outcome` | `hero_id`, `partner_hero_id`, `is_with` | `pair_lane_winrate`, `sample_size` | laneOutcome(heroId=hero1) → client-side filter to partner |
| `stratz.hero_matchup_ranking` | `hero_id`, `side: with\|vs`, `take`, `min_sample_size` | `matchup_ranking_row`, `sample_size` | heroVsHeroMatchup(heroId, take) |
| `stratz.lane_meta_global` | `is_with`, `min_sample_size`, `highlight_top` | `lane_meta_row`, `sample_size` | laneOutcome (no heroId) → handler aggregates + top-N |
| `stratz.hero_position_stats` | (none) | `position_stat` | stats(groupByPosition) |

Retire: `stratz.lane_outcome`, `stratz.hero_vs_hero_matchup` (no compat
layer, per AGENTS.md), `lane_outcome` / `matchup_win_rate` evidence kinds,
related contracts.

### 3. Tool output shape matches question shape — no raw records to LLM

- pair_lane_outcome: 1-row lookup, no `take`.
- hero_matchup_ranking: `take`-controlled, sorted top-N.
- lane_meta_global: **aggregate stats + top-N highlight**, never the raw
  120 rows.
- ToolResult gains `data_truncation` and `total_available` so the critic
  and planner can see whether an unseen tail exists.

### 4. Locked defaults (decided this round)

- `hero_matchup_ranking.take`: default 10, max 50; `min_sample_size` default 100.
- `lane_meta_global.highlight_top`: default 15; `min_sample_size` default 200.
- `pair_lane_outcome`: no take; no enforced min_sample_size, but the critic
  lowers confidence when < 50.

### 5. New plan-level critic rules

- Context-goal consistency: if goal names a bracket/time, `plan.context`
  must reflect it.
- Pair entity coverage: if goal names two heroes, plan must contain two
  `resolve_hero` plus a `pair_*` tool referencing both.
- confidence < threshold → `severity=failed` and `passed=false` (today's
  warning + passed=true is a bug).

### 6. Replan path

`total_available + data_truncation` surfaces truncation. When the target
entity is absent from returned records AND truncation is set, the critic
emits `replan_hint: "bump take on tool X"`. The planner adjusts only that
tool_call's `take`; QueryContext and other tool_calls are untouched. This
matches v2.5 §7.2 limits (`max_replans=1, max_tool_calls_total=8`).

### 7. Force claims in synthesizer

`natural_language_answer` must attach every number in `summary` to
`claims[].evidence_refs`, giving the critic a back-check path. Without
this the LLM free-text remains unverifiable.
