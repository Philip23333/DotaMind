## 本次完成的工作

### 1. 战队查询链路梳理

当前自然语言战队查询链路：

```text
POST /api/v1/query
  -> QueryService
  -> Orchestrator LLM function calling
  -> ReportRequest(task_type="team_report", team_name=原始提取值)
  -> ReportPipeline
  -> Retriever
  -> OpenDota team directory + deterministic resolution
  -> OpenDota team facts
  -> Analyzer
  -> Critic
  -> Formatter
  -> HTTP response
```

Orchestrator 只负责选择 `get_team_report` 并提取用户表达，例如 `"Team BB"`。它不生成或猜测 OpenDota `team_id`。

Retriever 负责把用户表达映射到 OpenDota 真实战队，并在解析成功后获取事实数据。

### 2. 确定性战队候选匹配

Retriever 新增多阶段确定性匹配：

1. 原始 name/tag 精确匹配
2. 忽略大小写、空格和标点
3. 去除 `Team`、`Esports`、`Gaming` 等通用词
4. 紧凑字符串匹配
5. CamelCase 缩写召回，例如 `BetBoom -> BB`
6. 使用 `SequenceMatcher` 进行模糊匹配
7. 按匹配强度返回唯一结果或歧义候选

解析结果为三态：

```text
resolved   -> 获得唯一 team_id，继续查询
ambiguous  -> 多个合理候选，返回候选列表
not_found  -> 没有合理候选
```

`Team BB` 当前可以召回：

```text
team_id=8255888  name=BB       tag=BB
team_id=9131584  name=BB Team  tag=BB
```

两个候选匹配强度相同时，系统不使用 rating 强行猜测，而是返回歧义。

### 3. 战队错误契约

战队查询不再使用固定 Team Spirit mock 掩盖失败：

| 场景 | HTTP 状态 | 错误码 |
|---|---:|---|
| 唯一匹配 | 200 | - |
| 多个合理候选 | 409 | `ambiguous_team` |
| 完全找不到 | 404 | `team_not_found` |
| live data 关闭或 OpenDota 不可用 | 503 | `team_data_unavailable` |

错误响应包含：

```json
{
  "error": "ambiguous_team",
  "message": "Multiple OpenDota teams matched 'Team BB'.",
  "requested_team": "Team BB",
  "candidates": []
}
```

Meta report 的 mock fallback 暂未调整；本次变更只移除了战队报告的静默 mock fallback。

### 4. OpenDota 激进拆分

删除原来的单文件：

```text

```

删除过渡期兼容层：

```text

所有旧代理方法和私有兼容方法
```

当前结构：

```text
app/integrations/opendota/
  __init__.py
  transport.py
  heroes.py
  teams.py
```

职责划分：

| 模块 | 职责 |
|---|---|
| `transport.py` | AsyncClient、API key、timeout、缓存、请求日志、连接关闭 |
| `heroes.py` | heroStats、角色推断、胜率和职业赛指标、hero_id 到名称映射 |
| `teams.py` | teams、matches、players、比赛详情、战队指标聚合 |

Retriever 现在显式装配三个组件：

```python
transport = OpenDotaTransport(base_url, api_key)
heroes = OpenDotaHeroes(transport)
teams = OpenDotaTeams(transport, heroes)
```

调用方式：

```python
self._opendota_heroes.get_stats_for_role(role)
self._opendota_teams.get_all()
self._opendota_teams.get_report_data(...)
```

项目内已不存在 `OpenDotaClient` 或旧方法引用。

### 5. 共享 HTTP 连接和应用生命周期

之前每个 OpenDota endpoint 都创建一个新的 `httpx.AsyncClient`，无法复用 TCP/TLS 连接。

现在 `OpenDotaTransport` 在第一次请求时懒加载一个共享客户端，英雄和战队模块共用同一连接池和缓存。

关闭链路：

```text
FastAPI lifespan
  -> QueryService / ReportService
  -> ReportPipeline
  -> Retriever
  -> OpenDotaTransport.aclose()
  -> httpx.AsyncClient.aclose()
```

当前配置：

```text
CACHE_TTL = 3600 seconds
REQUEST_TIMEOUT_SECONDS = 20
```

timeout 是每个独立 HTTP 请求的超时，不是整份战队报告的总超时。

### 6. OpenDota 请求诊断和日志脱敏

每个 OpenDota 请求现在记录：

```text
path
cache hit/miss
HTTP status
elapsed_ms
exception type
repr(exception)
```

示例：

```text
OpenDota request completed path=/teams/2163/players status=200 elapsed_ms=18180
OpenDota request failed path=/teams/2163/players elapsed_ms=20010 type=ReadTimeout error=ReadTimeout('')
```

HTTPX 日志过滤器会移除 URL 查询串，避免 API key 出现在控制台日志中：

```text
HTTP Request: GET https://api.opendota.com/api/teams/2163 "HTTP/1.1 200 OK"
```

未加入重试、退避或并发策略调整。

## 当前完整战队链路

```text
User query
  -> Orchestrator extracts team_name
  -> Retriever calls OpenDotaTeams.get_all()
  -> OpenDotaTransport GET /teams
  -> Retriever deterministic resolution
      -> resolved / ambiguous / not_found
  -> OpenDotaTeams.get_report_data()
      -> GET /teams/{team_id}/matches
      -> filter last N days, cap 30 matches
      -> GET /teams/{team_id}/players
      -> concurrent GET /matches/{match_id}
      -> OpenDotaHeroes.name_map()
      -> GET /heroStats
      -> aggregate record, heroes, players, duration and adaptation metrics
  -> Analyzer creates TeamReport
  -> Critic approves team report
  -> Formatter attaches OpenDota/live source
  -> HTTP response
```

## 已知问题

1. **OpenDota 上游波动**：`/teams/{id}/players` 曾出现 5 秒 `ConnectError` 和 20 秒 `ReadTimeout`，同一接口随后可能在 1 秒内成功。
2. **冷请求延迟高**：完整 Team Liquid 报告成功样本约 40 秒，其中 players 接近 20 秒。
3. **比赛详情并发**：最多并发查询 30 场详情；单场失败会被忽略，可能降低英雄统计样本完整性。
4. **歧义候选缺少交互闭环**：API 返回候选，但当前 request contract 还不能直接提交选中的 `team_id`。
5. **战队 Critic 较弱**：当前 Critic 对 team report 不做 evidence-level 审核。

## 下一步建议

1. 持续采集各 OpenDota path 的成功率、P50、P95 和错误类型，确认上游稳定性基线。
2. 为歧义响应增加 `team_id` 选择和重新查询契约。
3. 设计部分数据降级：players 或个别 match detail 失败时，明确标记缺失数据而不是中止全部报告。
4. 在有足够诊断样本后，再决定是否增加有限重试、退避和并发限制。
5. 为 team report 增加 evidence 和 Critic 校验。
