## 修改总结

- **目标**：把此前口头梳理的整体架构分层固化为可引用设计文档，方便后续讨论 validator、STRATZ 时间窗口、工具扩展和 answer/critic 边界时按层定位。
- **新增文档**（5 个文件，位于 `docs/design/`）：
  - `Planner层.md`：说明 Planner 从用户问题到 `ExecutionPlan` 的 prompt 构建、LLM envelope、Pydantic 校验、catalog 校验重试和 graph 路由。
  - `Validator层.md`：说明 Pydantic 与 catalog validator 的分工，以及 registry/tool/ref/args/output_contract/evidence/context scope 七段校验链路。
  - `Tool层.md`：说明 `ToolDefinition`、`ToolRegistry`、runtime `$ref` 解析、`ToolExecutor`、`QueryContext` 和 `ToolResult` 的执行链路。
  - `Evidence层.md`：说明 `ToolResult -> EvidenceItem -> EvidenceGraph` 的转换、missing evidence、data quality、STRATZ weekly bucket provenance 和 extractor 边界。
  - `Answer+Critic层.md`：说明 structured/natural answer 路由、自然语言 evidence-only prompt、data notes/confidence、critic 检查项和 response serialization。

## 关键对齐点

- 文档以 `docs/design/DotaMind_MVP_v2.5.md` 和 `docs/technical/architecture.md` 为准，强调 `intent` 不是路由键，执行只由校验后的 `tool_calls` 决定。
- 文档按当前工作树中的 `weeks_back` 语义描述 STRATZ 时间窗口：Planner 只表达相对周数，Tool 层解析已完成周，Evidence/Answer 保留 per-week provenance。
- 文档明确 Validator 不做业务路由、不执行工具、不 silent clamp；Tool 层不生成结论；Evidence 层不聚合跨周统计；Answer/Critic 不补工具。
