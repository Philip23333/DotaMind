# DotaMind 进度快照：2026-07-02 17:25

> 本文记录在 STRATZ evidence extractor 中注入英雄可读名称，以及清理 `lane_meta_global` 的 `position` 字段。

## 本次更新

- 在 `stratz_tools.py` 中新增缓存助手 `_hero_name_index()`：
  - 基于 `load_default_hero_resolver().heroes` 派生 `{hero_id: localized_name}`。
  - `lru_cache(maxsize=1)`，yaml 每个进程只解析一次。
- 给所有携带英雄 id 的 STRATZ evidence extractor 注入 `hero_name`（及 partner/target 对应字段）：
  - `lane_meta_global_evidence`：value 新增 `hero_name` + `target_hero_name`。
  - `pair_lane_outcome_evidence`：value 新增 `hero_name` + `partner_hero_name`。
  - `hero_matchup_ranking_evidence`：每行 value 新增 `hero_name` + `target_hero_name`。
  - `hero_position_stats_evidence`：value 新增 `hero_name`。
  - 所有受影响的 `subject` 字符串改为用英雄名（未知时回退到 id）。
  - 动机：用户不可能拿着 hero_id 再去查表。
- 清理 `stratz.lane_meta_global` 的 `position`：
  - handler 不再把 `context.position_ids` 透传给 `StratzHeroes.lane_outcome`。
  - 返回的每行数据剥离 `position`。
  - `filters` 块删除 `position_ids`。
  - evidence 的 id / subject / value 不再引用 `position`。
  - 动机：「强势对线组合」场景下该字段冗余——实际数据里所有行都是 `POSITION_1`，且其「lane bucket」语义并不能清楚指代 pair 中的任何一个英雄。
- 修复 `lane_meta_global_evidence` 的预存 bug：
  - 原来读 `hero_id1` / `hero_id2`（永远为 `None`），实际数据字段是 `_normalize_lane_outcome` 产出的 `hero_id` / `target_hero_id`。
  - 副作用：「强势对线组合」的 LLM 输出之前引用的 hero id 是从别处来甚至幻觉出来的；evidence 管道现在能正确喂入 id 和名称。

## 边界

- `pair_lane_outcome` 在 handler 输出和 evidence 中仍保留 `position`。该工具回答的是「特定英雄 pair 在特定路的胜率」，`position` 语义明确（这对出现在哪一路），因此不移除。
- hero_name 注入仅在 evidence 层。handler 输出的 row 数据仍是原始 `hero_id` 键（LLM 通过 `tool_results` 可见）。若后续观察到 LLM 仍输出原始 id，需要在 handler 输出层再加一层同样的映射。
- 未改 `resolve_hero_evidence`（本身已暴露 `localized_name`）。
- 未改 OpenDota / patch 工具。
