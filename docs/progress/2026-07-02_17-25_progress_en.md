# DotaMind Progress Snapshot: 2026-07-02 17:25

> This snapshot records hero-readable name injection across STRATZ evidence extractors and the cleanup of the `lane_meta_global` `position` field.

## Updates

- Added cached helper `_hero_name_index()` in `stratz_tools.py`:
  - Derives `{hero_id: localized_name}` from `load_default_hero_resolver().heroes`.
  - `lru_cache(maxsize=1)` so the yaml is parsed once per process.
- Injected `hero_name` (and partner/target variants) into all hero-bearing STRATZ evidence extractors:
  - `lane_meta_global_evidence`: value now carries `hero_name` + `target_hero_name`.
  - `pair_lane_outcome_evidence`: value now carries `hero_name` + `partner_hero_name`.
  - `hero_matchup_ranking_evidence`: per-row value now carries `hero_name` + `target_hero_name`.
  - `hero_position_stats_evidence`: value now carries `hero_name`.
  - All affected `subject` strings now render hero names (fall back to id if unknown).
  - Rationale: end users cannot be expected to translate `hero_id` themselves.
- Cleaned up `stratz.lane_meta_global` `position`:
  - Handler no longer forwards `context.position_ids` to `StratzHeroes.lane_outcome`.
  - `position` is stripped from each row in the returned data.
  - `position_ids` is removed from the `filters` block.
  - Evidence id / subject / value no longer reference `position`.
  - Rationale: for the "strong lane combos" feature the field is redundant — every row was `POSITION_1` in practice, and the semantics ("lane bucket") did not clearly attach to either hero of the pair.
- Fixed pre-existing bug in `lane_meta_global_evidence`:
  - Was reading `hero_id1` / `hero_id2` (always `None`) instead of the actual `hero_id` / `target_hero_id` keys produced by `_normalize_lane_outcome`.
  - Side effect: LLM output for "强势对线组合" previously cited hero ids from elsewhere or hallucinated; the evidence pipeline now feeds correct ids plus names.
